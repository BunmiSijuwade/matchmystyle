# Project Architecture Rules

- Results-to-Concierge handoff uses `src/lib/buildLookRequest.ts` to build a bounded query link from analysis only; Concierge remains responsible for reading the saved profile size so personalization has one existing source.

- Keep Shopping Concierge presentation in `src/components/concierge`; the page owns search state and the existing `shopify-catalog` function remains the sole verified product source, so UI changes cannot fabricate or mutate catalog facts.
- Treat Concierge image selection as preview-only until explicitly connected to the Analyzer image pipeline; visible labels must never imply interpretation or image search is active.
- All Results product cards (per-item tier matches and "Shop the aesthetic") come only from the existing `shopify-catalog` function via `src/lib/shopCatalog.ts`; `analyze-outfit` never returns products or URLs, so no shown product can be invented.
- The AI-styled look preview is an isolated prototype (`style-look` function + `LookStyledTab.tsx`, hooked in only as the tab in `LookCardDialog.tsx` and the "On a model · AI" view in `components/results/v2/LookStudio.tsx`, which mounts it only when picked) so it can be removed cleanly; it is labeled as an AI preview and never replaces real product images.
- The redesign is the default (Nov 10, 2026), with `?redesign=0` as a remembered way back to the previous design and `?redesign=1` to return (`src/lib/redesign.ts`). Redesigned screens live in `components/*/v2/` and are presentation only: they take state from the existing page, so product sourcing rules above still apply. New UI work goes in the redesign; remove the old screens and the switch once the way back is no longer needed.
- Expose agent tools only via `src/lib/mcp/` (bundled into the auto-generated `mcp` function); the server is public by user choice, so tools must stay read-only over public data and reuse `shopify-catalog` and `concierge-plan` rather than adding new data sources.

- All AI-cost calls go through `supabase/functions/_shared/rateLimit.ts`: one config for per-IP, per-function and a shared daily AI budget, kept in the `rate_limits` table via the service-role-only `hit_rate_limit_v2`. It fails closed and honours the `AI_ENABLED` / `STYLE_LOOK_ENABLED` flags, so spend has a hard daily ceiling even across many IPs. Callers must explicitly allow only the `ok` verdict; blocking reasons feed the shared notice builder. The MCP gets caller IP from a Deno.serve wrapper in `src/lib/mcp/request.ts` and forwards it (with `x-mms-internal`) to `concierge-plan`, so `style_me` counts against the same caps. The service key is used only for counters and `mcp_style_cache`, never for tool data.
- The Results "Your look" is assembled by pure rules in `src/lib/assembleLook.ts` from `useLiveMatches` tiers (no AI call); swaps and removals are local overrides, so the look can never show a product the catalog didn't return.
- Caller IP for rate limits comes only from `cf-connecting-ip` (verified unspoofable on the edge gateway; x-forwarded-for and x-real-ip are client-influenced or internal), so per-IP buckets can't be reset by headers.
- The MCP server stays read-only and never gets tools that read or write user data unless OAuth is added first.
- Any function that touches user data (saved looks, pieces, roles) checks the signed-in user inside the function with `supabase.auth.getUser()` and relies on row-level security, never on `verify_jwt` alone, because the publishable key is public.
- Every new public function gets a `RATE_LIMITS` entry and uses the shared CORS allowlist in `supabase/functions/_shared/cors.ts` (`withCors`); only `mcp` keeps the SDK's CORS.
